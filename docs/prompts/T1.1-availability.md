## MODELO DE DATOS (migración Alembic 0001, SQL explícito)
```
inventory(room_id uuid, hotel_id uuid, night date, total int not null check (total >= 0),
          held int not null default 0 check (held >= 0), confirmed int not null default 0 check (confirmed >= 0),
          primary key (room_id, night), check (held + confirmed <= total));  -- índice (hotel_id, night)
holds(hold_id uuid primary key, room_id uuid not null, check_in date not null, check_out date not null,
      units int not null check (units > 0), status text not null check (status in (HELD,CONFIRMED,RELEASED,EXPIRED)),
      expires_at timestamptz not null, created_at timestamptz not null default now(), updated_at timestamptz not null default now(),
      check (check_out > check_in));  -- índice parcial (expires_at) where status = HELD
```
Todos los tiempos se calculan con **`now()` de la BD** (no el reloj de la app): varias réplicas no deben discrepar.

## DOMINIO (Python puro, sin frameworks)
- `DateRange(check_in, check_out)`: valida `check_out > check_in` y `noches ≤ MAX_NIGHTS`; expone `nights()` = `[check_in, check_out)`.
- `Hold` y reglas de transición: `HELD → CONFIRMED | RELEASED | EXPIRED`; `CONFIRMED → RELEASED`; `RELEASED`/`EXPIRED` terminales. Funciones puras que reciben `now`.
- Errores de dominio: `InvalidDateRange`, `NoInventory`, `HoldConflict`, `HoldExpired`, `InvalidState`, `HoldNotFound`, `InventoryBelowCommitted`, y `DependencyUnavailable` (para fail-closed).

## APLICACIÓN
Puerto `InventoryStore` (Protocol): `put_inventory`, `search`, `create_hold` → `(hold, created: bool)`, `extend_hold`, `confirm_hold`, `release_hold`, `get_hold`, `expire_due(limit)`, `ping`. Casos de uso finos: validan entrada (rangos, `units` 1..`MAX_UNITS`, ttl 1..`HOLD_MAX_TTL_SECONDS`) y delegan. Sin lógica SQL aquí.

## INFRAESTRUCTURA (SQLAlchemy Core + psycopg 3, **síncrono**)
Una transacción por operación:
- **create_hold:** (1) `INSERT INTO holds … ON CONFLICT (hold_id) DO NOTHING RETURNING`; si no insertó, leer el existente: mismos parámetros → devolver (`created=False`), distintos → `HoldConflict`. (2) Si insertó: `SELECT … FROM inventory WHERE room_id=:r AND night >= :ci AND night < :co ORDER BY night FOR UPDATE`; exigir **una fila por cada noche** y `total − held − confirmed ≥ units` en todas; si no → `ROLLBACK` y `NoInventory` (la fila de `holds` desaparece con el rollback). (3) `UPDATE inventory SET held = held + :u` sobre esas filas. `expires_at = now() + ttl`.
- **confirm:** `SELECT hold FOR UPDATE`; `CONFIRMED` → devolver (idempotente); `HELD` vigente → mover `held → confirmed` por noche; `HELD` con `expires_at <= now()` o `EXPIRED` → `HoldExpired`; `RELEASED` → `InvalidState`; inexistente → `HoldNotFound`.
- **release:** `HELD` → restar `held`; `CONFIRMED` → restar `confirmed`; `RELEASED`/`EXPIRED` → devolver su estado sin cambios; inexistente → `HoldNotFound`.
- **extend:** solo `HELD` vigente; `expires_at = now() + ttl`; si no → `HoldExpired`.
- **expire_due(limit):** `SELECT … WHERE status=HELD AND expires_at <= now() FOR UPDATE SKIP LOCKED LIMIT :n`; libera `held` y marca `EXPIRED`. Seguro con varias instancias.
- **put_inventory:** upsert por noche `[from, to)`; no permitir `total < held + confirmed` (→ `InventoryBelowCommitted`, rollback completo).
- **search:** por `hotel_id` y rango, `available = MIN(total − held − confirmed)`; **solo** habitaciones con inventario en **todas** las noches pedidas; incluir las de `available = 0`.
- **Fail-closed:** `OperationalError`, `LockNotAvailable` (`lock_timeout`), `QueryCanceled` (`statement_timeout`) y timeout del pool se traducen a `DependencyUnavailable` → HTTP 503 con `Retry-After: 1`. **Nunca** asumir disponibilidad.
- Pool configurable (`DB_POOL_SIZE`, `DB_POOL_TIMEOUT`); documentar en `docs/variables.md` el cálculo `réplicas × pool + workers ≤ 100` conexiones.

## PRUEBAS: escríbelas PRIMERO y muéstralas fallando
**Unit** (sin BD): `DateRange`; transiciones de `Hold`; casos de uso con un doble de `InventoryStore`; API con el doble (códigos, formato de error, `X-Request-ID`).
**Integración** (PostgreSQL real vía `127.0.0.1:5433` con el rol `availability_svc`; el fixture recrea el esquema con Alembic y limpia por prueba):
1. **Concurrencia I1:** `total=5` en 3 noches; **50 hilos** con `hold_id` distintos y conexiones propias → exactamente **5 `HELD` y 45 `NoInventory`**; `held+confirmed ≤ total` en todas las noches.
2. **Rangos solapados:** 100 hilos con rangos aleatorios que se solapan parcialmente sobre `total` pequeño → **sin interbloqueos**, sin sobreventa; el único error permitido además de `NoInventory` es `DependencyUnavailable`.
3. **Idempotencia:** mismo `hold_id` ×10 concurrentes → 1 hold, `held` incrementado una sola vez, exactamente un `created=True`; mismo `hold_id` con otros parámetros → `HoldConflict`.
4. **Ciclo de vida:** confirm idempotente (`held→confirmed`); release desde `HELD` y desde `CONFIRMED` restaura el cupo; release repetido sin efecto; confirm tras release → `InvalidState`; hold inexistente → `HoldNotFound`.
5. **Expiración:** ttl 1 s; tras expirar, `confirm` → `HoldExpired`; `expire_due` libera el cupo y marca `EXPIRED`; `extend` antes de expirar funciona y después falla.
6. **Defensa en la BD:** un `UPDATE` directo que viole `held+confirmed ≤ total` lanza `IntegrityError`.
7. **put_inventory:** bajar `total` por debajo de lo comprometido → `InventoryBelowCommitted`, sin cambios parciales; ampliar rango funciona.
8. **search:** devuelve el mínimo por noche; excluye habitaciones con noches sin inventario; refleja holds y confirmaciones.
9. **Fail-closed:** (a) mantener un `FOR UPDATE` abierto en otra conexión más allá de `lock_timeout` → `create_hold` da `DependencyUnavailable` y **no deja estado parcial**; (b) apuntar el motor a un puerto cerrado → `/ready` 503 y `POST /holds` 503 con `Retry-After`.
**Contrato:** snapshot de `openapi.json` versionado; la prueba falla si el contrato cambia sin actualizarlo (`make snapshot-availability` lo regenera).
**Arquitectura:** `lint-imports` en verde.
