## MODELO DE DATOS (Alembic 0001, SQL explícito, en `payment_db`)
```
payments(id uuid pk, reservation_id uuid not null unique, idempotency_key text not null unique, request_hash text not null,
         amount_cents int not null check (amount_cents > 0), currency text not null, method text not null,
         status text not null check (status in (INITIATED,SUCCEEDED,DECLINED,FAILED_TECHNICAL,UNKNOWN,REFUNDED)),
         provider_ref text, created_at timestamptz default now(), updated_at timestamptz default now())
payment_attempts(id uuid pk, payment_id uuid references payments, attempt_no int, simulate text, outcome text, error text,
                 started_at timestamptz, finished_at timestamptz, unique (payment_id, attempt_no))
ledger(id uuid pk, payment_id uuid references payments, kind text check (kind in (CHARGE,REFUND)), amount_cents int,
       currency text, created_at timestamptz default now(), unique (payment_id, kind))
  -- trigger BEFORE UPDATE OR DELETE que lance excepción: el ledger es append-only
sim_provider_charges(idempotency_key text pk, provider_ref text, status text check (status in (APPROVED,DECLINED)),
                     amount_cents int, currency text, created_at timestamptz default now(), refunded_at timestamptz)
```
`sim_provider_charges` representa un sistema **externo**: se escribe en una transacción/conexión **independiente y con autocommit**, de modo que el "cobro" sobrevive aunque la transacción de `payment` falle.

## DOMINIO (Python puro)
Estados y transiciones: `INITIATED → SUCCEEDED | DECLINED | FAILED_TECHNICAL | UNKNOWN`; `UNKNOWN → SUCCEEDED | DECLINED | FAILED_TECHNICAL`; `FAILED_TECHNICAL → INITIATED` (reintento con la **misma** clave); `SUCCEEDED → REFUNDED`. `DECLINED` y `REFUNDED` son terminales. Errores: `IdempotencyKeyReused`, `InvalidState`, `PaymentNotFound`, `ValidationError`, `SimulationDisabled`, `DependencyUnavailable`. `request_hash` = hash de `{reservation_id, amount_cents, currency, method, token}` (**sin** `simulate`).

## APLICACIÓN
Puertos: `PaymentProvider` (`charge(key, amount, currency, token, simulate)`, `lookup(key)`, `refund(key)`; excepciones `ProviderTimeout` y `ProviderUnavailable`) y `PaymentRepository`. Casos de uso: `create_payment`, `get_payment`, `get_by_reservation` (reconcilia si está `UNKNOWN`), `refund_payment`, `reconcile_unknown(limit)`.

**Regla de oro: persistir antes de actuar.** `create_payment`: (1) validar que `Idempotency-Key == reservation_id` (si no, 422); (2) insertar `INITIATED` (o leer el existente; mismo hash → seguir, distinto → `IdempotencyKeyReused`); (3) registrar el intento; (4) llamar al proveedor; (5) guardar el resultado con **compare-and-set** (`UPDATE … WHERE id=:id AND status IN (:permitidos)`) y, si `SUCCEEDED`, insertar el asiento `CHARGE` **en la misma transacción**.
Réplica de una solicitud con la misma clave: `SUCCEEDED/DECLINED/REFUNDED` → devolver tal cual (200); `UNKNOWN` → intentar reconciliar y devolver; `FAILED_TECHNICAL` o `INITIATED` (proceso caído a mitad) → reintentar el cobro (el proveedor es idempotente por clave). `201` solo si esta solicitud creó la fila.
Reconciliación (`UNKNOWN`): `lookup(key)` → `APPROVED` ⇒ `SUCCEEDED`; `DECLINED` ⇒ `DECLINED`; **no existe** ⇒ `FAILED_TECHNICAL` (suposición documentada: el proveedor simulado es consistente; uno real exigiría esperar y conciliar contra extractos).

## PROVEEDOR SIMULADO (`infrastructure/provider_sim.py`)
`charge` es idempotente por `idempotency_key` (PK de `sim_provider_charges`: repetir devuelve el cargo existente). Modos de `simulate` (solo si `PAYMENT_SIMULATION_ENABLED=true`; si no y llega un modo ≠ `ok` → 422 `SIMULATION_DISABLED`):
- `ok` → registra `APPROVED` y responde.
- `decline` → registra `DECLINED` y responde.
- `error_before_processing` → lanza `ProviderUnavailable` **antes** de registrar nada.
- `process_then_drop_response` → registra `APPROVED` y **luego** lanza `ProviderTimeout`.
- `slow` → registra `APPROVED`, duerme `PROVIDER_SLOW_SECONDS` y responde.
La llamada se ejecuta con timeout `PROVIDER_TIMEOUT_SECONDS` (p. ej. en un `ThreadPoolExecutor` con `future.result(timeout)`); al vencer → `ProviderTimeout` ⇒ `UNKNOWN`, y el hilo termina su efecto (el cargo queda registrado, como pasaría con un proveedor real).

## API (exactamente `docs/05-contratos-api.md` §7)
`POST /payments` (`Idempotency-Key` obligatoria), `GET /payments/{id}`, `GET /payments?reservation_id=`, `POST /payments/{id}/refund` (idempotente; solo desde `SUCCEEDED`, si no `409 INVALID_STATE`; ya `REFUNDED` → 200), `GET /health`, `GET /ready`. Error `{"error":{code,message,request_id,details}}`, `X-Request-ID`, logs JSON. Si la BD falla ⇒ **503 fail-closed** con `Retry-After`. Un fallo del proveedor **no** es 503: es un resultado de negocio (`FAILED_TECHNICAL`/`UNKNOWN`) con HTTP 200. **No** se expone por el gateway.

## PRUEBAS: escríbelas PRIMERO y muéstralas fallando
**Unit:** transiciones del dominio (válidas e inválidas); hash de solicitud (excluye `simulate`); casos de uso con repositorio y proveedor falsos para **cada modo**; **crash entre cobro y persistencia** (el falso lanza tras `charge` exitoso → el estado queda `INITIATED`; el reintento con la misma clave termina en `SUCCEEDED` con **un** asiento).
**Integración** (PostgreSQL real, rol `payment`):
1. `ok` → `SUCCEEDED`, 1 asiento `CHARGE`, 1 cargo en el proveedor.
2. `decline` → `DECLINED` terminal; repetir devuelve `DECLINED` sin nuevo cargo.
3. `error_before_processing` → `FAILED_TECHNICAL`, **0** cargos en el proveedor; reintento con la misma clave y `ok` → `SUCCEEDED`.
4. `process_then_drop_response` → `UNKNOWN`; `GET ?reservation_id=` reconcilia a `SUCCEEDED`; **1** cargo y **1** asiento.
5. `slow` (> timeout) → `UNKNOWN`; el worker lo reconcilia a `SUCCEEDED` sin llamada HTTP.
6. **Concurrencia I3:** 10 hilos con la misma clave → 1 fila, **1** cargo en el proveedor, **1** asiento, respuestas consistentes; repetir 20 veces sin fallos.
7. Clave ≠ `reservation_id` → 422; misma clave con cuerpo distinto → 422 `IDEMPOTENCY_KEY_REUSED`; segunda reserva con otra clave pero mismo `reservation_id` → rechazo por `UNIQUE`.
8. Reembolso: desde `SUCCEEDED` → `REFUNDED` + asiento `REFUND` único; repetido → 200 sin nuevo asiento; desde otros estados → 409.
9. `ledger`: `UPDATE`/`DELETE` directos fallan (trigger).
10. Verificación SQL de **I3**: ningún `reservation_id` con más de un `CHARGE`; todo `SUCCEEDED` tiene su asiento.
11. `PAYMENT_SIMULATION_ENABLED=false` + `simulate=decline` → 422.
12. Fail-closed: BD inaccesible → `/ready` 503 y `POST /payments` 503 con `Retry-After`; **no** queda estado parcial.
